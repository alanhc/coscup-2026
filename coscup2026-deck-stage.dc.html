From first principles

What is firmware development, irreducibly?

01
Firmware is only true on real hardware.
No simulator is the device. A change is unproven until it boots on the board.
02
Device-level validation needs a full image.
AOSP can build single modules — but to validate on hardware you still rebuild, flash, and boot. One-line change, same loop.
03
So one hypothesis costs one full cycle.
sync → build → flash → verify, every single time.
THEREFORE

Progress is measured in verified loops, not lines of code.

Three loops, three clocks, three deciders

agentic coding loop minutes the agent decides — runs until the check passes
developer feedback loop hours the human decides — direction, spec, acceptance
external feedback loop days + users decide — the loop no one can automate

The firmware build loop straddles the first two: hours of wall time, minutes of judgment, scattered unpredictably. That mismatch is exactly why where the boundary goes matters more here than anywhere.

Part 2 · From criteria to implementation

Three words people use interchangeably

The criteria say where the boundary goes. These three decide what you write it in.

CLI does the work Deterministic tools. fastboot · repo · adb
MCP does the wiring A protocol that hands tools and data to the model at runtime.
Skill holds the procedure A markdown file plus scripts: what to do, in what order, and where to stop.

Which means my boundary ships as one sentence in a file: “ask me before any flash; never flashall — per partition, slot spelled out.”

Why writing it down works · SDD, 2025–26

The spec is the prompt

VIBE CODING
Prompt loosely, ship what comes back.
Plausible code that drifts from intent — no acceptance criteria, so review never ends.
The prompt is spent the moment it runs.
SPEC-DRIVEN
Write what & how-to-verify first — versioned, reviewed; the agent executes against it.
A SKILL.md is this spec for the build pipeline: outputs, checks, stop points.
The spec is an asset — edit it, re-run the loop.

Why it raises quality is criterion two again: acceptance criteria make output verifiable — and verifiability is what lets automation go high. The prompt was never the point; the loop’s termination condition is. Now the default everywhere: Spec Kit, Kiro, Claude Code — and the community got there first with Superpowers, skills that block coding until the spec exists.

How it handles failure

a step fails
→ is there a known recovery path?
agent handles Predictableyes →
network drop → retry
repo sync stall → lower parallelism
stop + notify Unexpectedno →
no matching tag → halt
compile error → halt, full log attached
boot hang → halt: adb is gone, UART is the only witness

Why the right column is human: a log is not truth, it is hardware behavior serialized — wrong baud rate reads as garbage, TX alive says nothing about RX, early boot exists only on the serial console. The agent reads the strings; the engineer knows how the strings got there.

Open source is already drawing the boundary

Linux kernel Apr 2026
Use it — a human signs.
Only humans may sign the DCO. AI help declared with an Assisted-by tag. Submitter keeps full responsibility.
→ accountability, made policy
GCC Jul 2026
Not in contributions.
Declines legally significant LLM-generated or -derived code (FSF threshold, ≈15 lines). Hand-cleaning doesn’t exempt it. Test cases may pass.
→ provenance: what verification can’t buy
curl Jan 2026
Drowned — gates closed.
Bug bounty ended after AI-slop reports crushed a 7-person team. Confirmation rate fell from 15% to under 5%.
→ unverified agent output = DoS on maintainers

Three projects, three lines — all the same shape: a human signs, output must be verifiable, provenance must be answerable. Before you point an agent upstream, read the project’s AI policy — many major projects have one now.
